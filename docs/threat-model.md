# Modelo de amenazas y contrato W09 (#92)

## Corte y alcance

Contrato documental para [#93](https://github.com/Draggodeidad/pwa-utt/issues/93) (controles/CI), [#95](https://github.com/Draggodeidad/pwa-utt/issues/95) (pruebas) y [#99](https://github.com/Draggodeidad/pwa-utt/issues/99) (robots). Describe el código de `3fc20505f7cb8f3e25b795884d28fee9f94cd881` más el baseline `0ec32eb892bb49a0747eb3792f541b0d5aa9ebbd`, punto de partida de `feat/w09`. **Una decisión de este contrato no equivale a un control implementado ni a un resultado de prueba.** Los casos W09 comienzan pendientes.

Fuente: [baseline #91](w09-baseline.md), [inventario de 308 archivos](w09-repository-inventory.tsv) y ZIP local `PWA-w09-kit-estudiante.zip`, 8380 bytes, SHA-256 `a641eb48fc8f0a74d4ac13ca16a53bb205915dc878bfc2b9f2839d04a6a2d28d`. Se contrastaron sus ocho archivos y contratos: no contiene plantilla de amenazas, reglas CSP/robots ni suite ejecutable. La distribución original y la hora oficial de entrega no son verificables con el ZIP.

Sólo se describen categorías y escenarios sintéticos, sin credenciales ni registros reales. No es auditoría profesional, certificación legal, prueba de penetración ni garantía de ausencia de PII. El [inventario de privacidad](privacy-data-inventory.md) distingue los fixtures sintéticos de configuración, credenciales y activos de procedencia no acreditada. Estos últimos impiden afirmar que todo el repositorio cumple ya la regla sintética.

Flujo principal: persona → PWA → IndexedDB/cola → API Next → Auth/perfil → RPC/RLS → Postgres; las fotos pasan además por decodificación Next → Storage privado. El ACK vuelve a una transacción local de la partición vigente. El SW sólo guarda shell/recursos públicos. GitHub → build/postbuild → hosting publica código y activos estáticos; no convierte esos activos en privados.

Supuestos: navegador/OS y hosting no comprometidos, operador autorizado configura migraciones/bucket, HTTPS externo se verifica antes del despliegue y cuentas de demostración son sintéticas. Un atacante con sesión legítima puede manipular cualquier request; se modela también XSS, errores de configuración y uso compartido. Administrador de Supabase/hosting y quien controla el perfil del navegador pueden acceder a información fuera de las restricciones de la aplicación.

## Matriz estable de amenazas

Prioridad cualitativa, sin puntaje inventado: **alta** = exposición de sesión/datos, bypass de autorización o contradicción comprobada del contrato; **media** = requiere condición adicional o afecta disponibilidad/privacidad acotada. Impacto A/M = alto/medio; probabilidad A/M/B = alta/media/baja, con razón por fila. El riesgo residual es una valoración de diseño, no resultado empírico. Todos los cambios y validaciones nuevas quedan pendientes; las pruebas enlazadas son evidencia reutilizable de controles existentes, no PASS W09.

### Adaptador de error de configuración (#93)

Aclaración aditiva antes de implementar: `supabase/config.ts` exporta `SupabaseConfigurationError extends Error`, reexportada por `security/config.ts`. Las firmas existentes no cambian. `supabase/server.ts` ofrece `withSupabaseConfiguration(handler)` para envolver los handlers HTTP y middleware: captura únicamente ese error tipado, responde 503 `Servicio no disponible` con `private, no-store` y no registra el error/entorno. Otros errores conservan su tratamiento. Esto cierra la brecha observada: la creación del cliente ocurre fuera del try en APIs y middleware y hoy produce 500/log de Next. No cambia autorización ni introduce clientes sintéticos.

### Validación: decisión de frontera y transporte

1. Reducir en las fuentes canónicas [inspection.schema.ts](../src/features/inspections/schemas/inspection.schema.ts) y [finding.schema.ts](../src/features/findings/schemas/finding.schema.ts) los máximos de **summary 3000, description 3000, title 160**, tanto captura/actualización como finalización. No modificar constraints SQL para aceptar más. Conservar el trim y reglas de campos obligatorios existentes. Revisar atributos UI que pudieran ofrecer límites mayores. Borradores locales anteriores fuera de límite requieren corrección explícita; no truncarlos ni descartar cola silenciosamente.
2. Unidad del validador existente: `String.length` (UTF-16), SQL `char_length` cuenta caracteres. La decisión es un límite local conservador: nunca admite por longitud algo mayor a SQL, aunque caracteres astrales consumen dos unidades y se rechazan antes. Probar ASCII exactamente N/N+1 y astrales N/2 y N/2+1; no prometer equivalencia Unicode absoluta ni cambiar esta semántica accidentalmente en un refactor.
3. Allowlists de nombres, no un límite genérico que permita campos extra: sobre común sólo `clientId, kind, entityId, baseVersion, payload` (cinco); idempotencia en header aparte. Payloads exactos: inspección create/update `laboratoryId, inspectionDate, summary`; finalize `expectedFindingIds, location`; discard y finding.delete vacíos; finding.create `inspectionId, title, description, priority`; finding.update `title, description, priority`; followup `priority, status`; photo.upload `inspectionId, findingId, sourceHash, mimeType, bytes`; photo.delete `inspectionId, findingId`. Location sólo `latitude, longitude, accuracy, capturedAt`; coordinación sólo `action, baseVersion, notes, confirmation`, con restricciones por acción existentes. Cero claves extra en cualquier nivel. `ownerUserId`, `role`, timestamps y folio no dan autoridad si llegan del cliente.
4. Mantener UUID/versión, kind por endpoint y coincidencia `entityId`/ruta. Entrada inválida → 422; origen ausente/host, puerto o protocolo distinto → 403; sin mutación. JSON malformado y MIME inválido no llegan a RPC. El parser actual usa `startsWith('application/json')`: por lectura admite prefijos como `application/json-extra`. #93 debe comparar el media type completo, sin parámetros, con `application/json` (case-insensitive; permitir `; charset=utf-8`); #95 verifica rechazo del prefijo falso. No añadir CORS amplio. Un error de dominio usa mensajes seguros existentes; los nombres de campo no deben interpolar valores del payload.
5. `readJsonMutation` hoy limita `Content-Length` declarado a 4096 y `request.text().length` a 4096; coordinación pasa 16384. **No es límite uniforme de bytes ni streaming.** Conservar esos valores en W09 y probar ambos mecanismos por separado (header omitido, en límite y excedido); un payload válido de dominio puede exceder el sobre HTTP, en particular UTF-8 multibyte o varios campos largos. No anunciar aceptación HTTP de todas las combinaciones máximas. Esta limitación queda en T01; límites de hosting/memoria se verifican aparte.
6. Fotos: 1–5242880 bytes (5 MiB), máximo tres activas por hallazgo, JPEG/PNG/WebP reales de una página, hasta 25 millones de píxeles y timeout de recodificación 5 s. El límite de bytes se aplica durante lectura; MIME/metadata no sustituyen decodificación. `x-photo-operation` tiene tope existente de 4096 caracteres. Probar el límite de transporte con stream sintético y la recodificación con imagen sintética válida por separado; bytes de relleno no son una imagen válida.

### Secretos y configuración: política cerrada

- Variables de aplicación admitidas: **`SUPABASE_URL` y `SUPABASE_ANON_KEY`**, sólo en servidor. `NODE_ENV` selecciona headers de Next; no es credencial. No crear aliases `NEXT_PUBLIC_*`, claves `service_role`/`sb_secret_`, contraseñas o tokens de usuario en configuración/fixtures. Variables técnicas de CI/reportes no deben copiarse al bundle ni al reporte como un dump.
- Recortar espacios exteriores; vacío/ausente falla antes de crear cliente y sin fallback sintético. No resolver DNS ni llamar a Supabase durante validación. No fallar al importar/build por no tener entorno: validar al solicitar config.
- URL: máximo **2048 caracteres** tras trim, rechazar controles/espacios internos, parsear con `new URL`; protocolo https, host no vacío, sin username/password, query ni fragmento, pathname sólo `/`; devolver `url.origin` sin slash final. `http` se admite únicamente para host exacto `localhost`, `127.0.0.1` o `[::1]`, incluso al levantar `next start` sintético. Puerto explícito permitido si el parser lo acepta. Rechazar representaciones alternativas numéricas de loopback, hostname con punto final y URLs relativas. El valor original debe tener autoridad canónica; no admitir credenciales/ruta escapadas que el parser normalice silenciosamente.
- La excepción loopback permite desarrollo/arneses locales; **un despliegue remoto debe usar HTTPS**. No permite HTTP a redes privadas, comodines ni subdominios `*.localhost`. HTTPS puede apuntar al host Supabase configurado por operador: no se incorpora al CSP del navegador. La config no es una frontera contra un operador malicioso/SSRF con control del entorno.
- Clave: máximo **4096 caracteres ASCII** tras trim, sin espacios internos ni controles. Admitir sólo `sb_publishable_` seguido de uno o más caracteres `[A-Za-z0-9_-]`, o JWT legado de tres segmentos base64url no vacíos cuyo header/payload sean objetos JSON y cuyo payload tenga `role === 'anon'`. Rechazar `service_role`, `sb_secret_`, JWT de sesión (`authenticated`), formatos opacos desconocidos y longitud máxima + 1. La lectura del claim es una barrera de configuración, **no verifica firma**; la autenticidad/validez remota la verifica Supabase. Los fixtures de tests deben fabricarse localmente y nunca ser claves funcionales.
- Error de configuración sólo identifica variable y motivo fijo, nunca valor, URL completa, JWT/claims, stack de SDK ni objeto de entorno. No loguear cookies/Authorization, passwords, payloads, GPS o blobs. UI/API: `503 Servicio no disponible` por configuración inválida; no devolver el error crudo ni simular sesión. Verificar stdout/stderr/HTTP/reportes con centinelas sintéticos; no publicar esas salidas si detectan una filtración.
- `.env.example` mantiene sólo placeholders, `.env*` sigue ignorado excepto ejemplo, sin imprimir entornos locales ni añadir credenciales a Git. Una clave filtrada requiere revocación/rotación por el operador; borrar una línea no borra historia ni artefactos. Inspección de diffs/bundles y revisión humana siguen siendo necesarias; no afirmar scanner exhaustivo.

Tipos de claves y bypass RLS contrastados con [documentación oficial de Supabase](https://supabase.com/docs/guides/getting-started/api-keys). La política local mantiene mínimo privilegio aun en servidor; no adopta una clave privilegiada porque esté allí.

### CSP y cabeceras por directiva

Aplicar `Content-Security-Policy` efectiva, no sólo Report-Only. Valores de producción exactos siguientes; comparar como directivas/tokens para no depender de espacios/orden del header. No duplicar directivas ni políticas contradictorias.

| Directiva | Producción | Justificación y límite |
| --- | --- | --- |
| `default-src` | `'self'` | Fallback del mismo origen; sin CDN/hosts implícitos. |
| `base-uri` | `'self'` | Impedir base externo. |
| `object-src` | `'none'` | No se usan plugins/objetos. |
| `frame-ancestors` | `'none'` | La PWA no se embebe; reduce clickjacking. |

| `script-src` | `'self' 'unsafe-inline'` | Excepción explícita por scripts inline de arranque/hidratación de Next 14 App Router, incluidos datos Flight. Sin `unsafe-eval`, `data:`, `blob:` ni hosts terceros. Riesgo XSS residual alto. |

| `manifest-src` | `'self'` | Manifest local. |

Desarrollo: única diferencia autorizada, agregar `'unsafe-eval'` a `script-src` para tooling dev y `ws: wss:` a `connect-src` para HMR. No trasladar esos tokens a producción. `getSecurityHeaders({ production: true })` debe ser determinista aunque el proceso de prueba tenga otro `NODE_ENV`.

Cabeceras adicionales exactas: `X-Content-Type-Options: nosniff` y `Referrer-Policy: no-referrer`. Mantener `Cache-Control: private, no-store` de respuestas privadas y flags de cookies existentes. No imponer `upgrade-insecure-requests`/HSTS desde un booleano que también se usa en `next start` HTTP local; HTTPS, redirección HTTP→HTTPS y HSTS del hosting se verifican por separado en la URL remota. No declarar transporte remoto cumplido por una build local.

La [guía oficial de CSP de Next 14](https://nextjs.org/docs/14/app/building-your-application/configuring/content-security-policy) explica el uso de nonces y render dinámico. Elegimos compatibilidad estática acotada para W09; nonces por request implicarían otro cambio de middleware/renderizado/caché. Esta excepción no demuestra protección completa XSS. #95 debe verificar hidratación/login, edición, apertura de diálogo, preview de foto y offline; si falla, diagnosticar el recurso exacto antes de ampliar la política. No introducir un wildcard como reparación automática.

### Política definitiva de rastreo para #99

`public/robots.txt` debe contener exactamente estos 26 bytes UTF-8/ASCII, LF y salto final, sin BOM, comentarios, sitemap ni rutas sensibles:

```text
User-agent: *
Disallow: /
```

Decisión: la PWA no publica contenido para indexación. `robots.txt` sólo solicita no rastrear; un bot puede ignorarlo. **Sesión/API/RLS siguen protegiendo rutas privadas.** No usar robots como control de confidencialidad ni como remedio de T10.

#99 crea exclusivamente el archivo. #93 agrega al matcher la exclusión **exacta** `robots\\.txt$` junto a las existentes, sin excluir `/robots`, `/robots.txt/privado` ni prefijos parecidos. #95 prueba GET sin sesión y con cookie de logout bloqueado → 200, `text/plain` (charset permitido) y cuerpo exacto, sin Location/login. Comprobar por separado una página privada y `/api/inspections` anónimos. Next puede normalizar slash final: registrar el redirect, seguirlo y exigir la respuesta canónica; no convertirlo en excepción amplia de auth.
